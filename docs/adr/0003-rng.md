# ADR 0003 — Generador de números aleatorios inyectable

- Estado: Aceptada
- Fecha: 2026-05-12

## Contexto

El programa original usa `RND(1)` global de Microsoft BASIC, sin
`RANDOMIZE`. Esto le da determinismo accidental: dos ejecuciones
producen el mismo laberinto, lo cual era una *feature* en 1978 (podías
imprimir el listado del laberinto y dárselo a otra persona con
confianza de reproducirlo). En 2026, queremos:

- Determinismo opcional (`--seed N`).
- Tests reproducibles.
- Posibilidad de cambiar la fuente de azar sin tocar dominio.

## Opciones

1. `random.random()` global. Mata la testabilidad.
2. `random.Random` instanciado en cada caller. Mejor, pero acopla la
   capa al stdlib.
3. **`Protocol` `Rng` en dominio**, implementado por adaptadores en
   `infrastructure.rng`. Inversión de dependencia clásica.

## Decisión

Opción 3. Definimos:

```python
class Rng(Protocol):
    def randrange(self, start: int, stop: int) -> int: ...
    def choice[T](self, seq: Sequence[T]) -> T: ...
```

Con dos implementaciones en `infrastructure.rng`:

- `StdlibRng(seed: int | None)` — wrapper sobre `random.Random`.
- `FixedSequenceRng(values: Iterable[int])` — devuelve una secuencia
  predefinida; útil para tests unitarios deterministas sin tener que
  recurrir a `random.Random(42)`.

## Consecuencias

- Dominio nunca importa `random`.
- Tests de propiedad con `hypothesis` pueden inyectar `StdlibRng(seed)`
  con seeds aleatorios.
- Si en el futuro queremos un RNG basado en `secrets` (mazes
  criptográficamente impredecibles para algún caso loco), basta con
  añadir un adaptador.
